# Feature Specification: Findings Dashboard — Presentation & UX v2

**Feature Branch**: `002-findings-dashboard-ux`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "The current implementation is very simplistic.
Take the dashboard further — a designed, navigable, filterable presentation of
the same findings — without reinventing the wheel and without breaking the v1
guarantees."

## Context

`001-findings-dashboard` (backlog D7) shipped and converged: a curated
`findings/*.toml` layer, a stdlib-only Python generator, and a single
self-contained `site/index.html` with three views (live lineup, candidate
status board, settled dead ends). Every displayed number resolves from
`results/*.json` at generation time and carries a what/how/evidence tooltip
with links to its FINDINGS.md section and raw source; missing or drifted
sources flag stale and exit non-zero.

V1 was deliberately bare (constitution VI, KISS/YAGNI): plain tables, one crude
bar chart, no navigation, no filtering, "clean readable default" only. In use
that bareness now costs trust and speed — the page is one long scroll, the sole
chart clips its top value label, only decode speed is compared, and there is no
way to narrow to one model or status. This feature makes the **same data** look
and behave like a tool a first-time reader wants to use, while keeping every v1
correctness guarantee intact.

Settled design decisions (2026-09-22, with the owner):

- **Same walls as v1.** One self-contained static `site/index.html`, opens from
  `file://`, no server, no network at view time; a stdlib-only Python
  generator; deterministic output (only the "generated at" stamp may differ).
  No new backend, no data model change is required by this feature.
- **Enhancement, not replacement.** All v1 requirements (evidence-backed
  numbers, tooltips, stale flags, read-only, deep links) continue to hold. v2
  is additive presentation and in-browser interaction over the existing render.
- **Interactivity is client-side and progressive.** Navigation, filtering,
  search, and sorting run as inline JavaScript in the browser at view time;
  they never change the generated bytes and never touch the filesystem. With
  JavaScript disabled the full content — every number, every tooltip's text,
  every link — is still present and readable.
- **Charts stay zero-dependency.** Richer comparison charts are still generated
  as inline SVG in Python (v1 research R2); no charting library is added.
- **Accessibility is a first-class target: WCAG 2.1 AA.**

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Jump between views without scrolling (Priority: P1)

The reader lands on the dashboard and sees a persistent navigation control that
names the three views (live lineup, candidate status board, settled dead ends)
and lets them jump to any one in a single action, from anywhere on the page.

**Why this priority**: The page is one long document; the status board and dead
ends are below a tall lineup. Without navigation the two views a new session
most needs — "what's shipped" and "what not to re-try" — are the hardest to
reach. Navigation is also the frame the other v2 features hang on.

**Independent Test**: Generate the site; from the bottom of the page, activate
each navigation target and confirm focus/scroll lands on the corresponding
view heading; confirm the same works by keyboard alone and with JavaScript
disabled (anchor links still resolve).

**Acceptance Scenarios**:

1. **Given** the generated site, **When** the reader activates a navigation
   entry, **Then** the corresponding view (`#lineup`, `#board`, `#dead-ends`)
   is brought into view and its heading receives focus.
2. **Given** keyboard-only operation, **When** the reader tabs to and activates
   a navigation entry, **Then** the same jump occurs with a visible focus
   indicator and no pointer required.
3. **Given** JavaScript is disabled, **When** the reader activates a navigation
   entry, **Then** it still resolves as a plain in-page anchor link.
4. **Given** an empty findings layer, **When** the site is generated, **Then**
   navigation still renders and each target leads to its view's empty state.

---

### User Story 2 - A designed, legible page instead of a bare one (Priority: P1)

The reader sees a page with clear visual hierarchy: a distinct header, visually
separated views, tier and status grouping that reads at a glance (quality /
fast / additive; shipped / on-trial / retired / dead-end / open), consistent
typographic scale and spacing, and status badges and stale/no-measurement
markers that are legible by shape and text, not colour alone.

**Why this priority**: "Very simplistic" is the stated problem. A number the
reader does not trust visually is a number they re-check by hand; a designed
surface is what makes the evidence feel auditable at a glance. This is the core
value of v2.

**Independent Test**: Generate the site; confirm each view is a visually
distinct region with a heading; confirm tiers and statuses are grouped and
labelled; confirm every badge/marker carries a text label (not colour only)
and meets the contrast bar; confirm nothing is truncated.

**Acceptance Scenarios**:

1. **Given** the generated site, **When** the reader views it, **Then** each of
   the three views is a visually distinct, headed region, and lineup findings
   are grouped and labelled by tier.
2. **Given** any status badge or stale / "no measurement" marker, **When** the
   reader views it, **Then** its meaning is conveyed by text (and shape), never
   by colour alone, and its text meets WCAG 2.1 AA contrast.
3. **Given** long model names, long tooltip text, or non-ASCII content, **When**
   the page renders, **Then** content wraps and renders intact with no
   truncation or overlap.
4. **Given** two runs over identical inputs, **When** the site is generated,
   **Then** the output is byte-identical except the "generated at" stamp — the
   redesign introduces no new non-deterministic field.

---

### User Story 3 - Comparison charts that are correct and comparative (Priority: P1)

The reader sees headline metrics compared across models in charts that are
readable and correct: no clipped or overlapping labels, a value axis with
gridlines, and comparisons for more than one metric (e.g. decode speed,
accuracy, context ceiling), each chart element carrying the same tooltip and
source links as its table counterpart.

**Why this priority**: The one v1 chart clips its top label ("58.8" is cut off)
and compares only decode speed, so the chart currently subtracts trust instead
of adding it. Correct, multi-metric comparison is the fastest way to read the
lineup.

**Independent Test**: Generate the site; for each chart, confirm every bar's
value label is fully visible within the SVG viewport, a value axis is present,
and each bar's tooltip and links equal its table row's; confirm a charted value
is never shown that is not also in a table with a tooltip.

**Acceptance Scenarios**:

1. **Given** a comparison chart, **When** it renders, **Then** no value label,
   axis label, or model label is clipped by the SVG viewport or overlaps
   another, at the generator's default width.
2. **Given** headline metrics beyond decode speed exist in the lineup findings,
   **When** the site is generated, **Then** a comparison chart is produced for
   each such headline metric that has at least two models to compare.
3. **Given** a chart element, **When** the reader hovers or focuses it, **Then**
   it carries the same what/how/evidence tooltip and FINDINGS/raw links as the
   corresponding table row, and the charted value equals the table value.
4. **Given** a headline metric with only one model, **When** the site is
   generated, **Then** it is not forced into a comparison chart (a single-bar
   chart implies no comparison and is omitted or clearly labelled as one model).

---

### User Story 4 - Filter and search to the finding you want (Priority: P2)

The reader narrows the page in the browser — by model, by tier, by status, and
by free-text over titles and rationales — and the views update live to show
only matching findings, with a visible count and a one-action clear. No page
reload, no network.

**Why this priority**: The board and dead-ends lists grow with every
experiment; "show me only gemma", "only dead-ends", or "find the co-residency
finding" is the difference between a scannable tool and a wall of text. It also
future-proofs the page against the findings layer growing (D8).

**Independent Test**: Generate the site; apply each filter kind and a text
query; confirm only matching findings remain across all views, a match count is
shown, clearing restores the full page; confirm it works by keyboard and causes
no network request.

**Acceptance Scenarios**:

1. **Given** the generated site, **When** the reader selects a model, tier, or
   status filter, **Then** all three views show only findings matching the
   active filters, and non-matching findings are hidden.
2. **Given** a free-text query, **When** the reader types it, **Then** findings
   whose title or rationale match are kept and others hidden, updated live.
3. **Given** an active filter or query that matches nothing, **When** it is
   applied, **Then** an explicit "no findings match" message is shown with a
   clear/reset control, not a blank page.
4. **Given** any active filter, **When** the reader clears it, **Then** the full
   unfiltered page is restored, and no filter state persists across a reload
   (the generated document is the source of truth).

---

### User Story 5 - Sort tables by any column (Priority: P2)

The reader clicks a column header (metric, value, model, status) to sort that
table, ascending then descending, respecting each metric's direction (higher-
or lower-is-better) so "best first" is meaningful. Numeric columns sort
numerically, not as strings.

**Why this priority**: "Which model decodes fastest?" or "order the board by
status" should be one click, not a manual scan. Sorting is the table-level
complement to filtering.

**Independent Test**: Generate the site; sort each sortable table by each
column both directions; confirm numeric columns order numerically and the sort
indicator reflects the active column/direction; confirm keyboard operation.

**Acceptance Scenarios**:

1. **Given** a table with more than one row, **When** the reader activates a
   column header, **Then** the rows reorder by that column, toggling
   ascending/descending on repeat activation, with a visible sort indicator.
2. **Given** a numeric column (e.g. a metric value), **When** it is sorted,
   **Then** rows order by numeric value, not lexicographically, and stale /
   "no measurement" rows sort to a consistent, documented position.
3. **Given** keyboard-only operation, **When** the reader focuses and activates
   a column header, **Then** the sort applies with a visible focus indicator.
4. **Given** JavaScript is disabled, **When** the page loads, **Then** each
   table renders in a stable, documented default order and remains readable.

---

### Edge Cases

- **Filter matches nothing** → explicit "no findings match" state with a reset
  control; never a blank page.
- **Single-row table / single-model metric** → sort controls are inert or
  hidden; no comparison chart is implied for one model.
- **JavaScript disabled** → all numbers, tooltip *text*, links, badges, and the
  three views are present; navigation degrades to anchor links; tables show
  their default order; filter/sort/search controls are absent or inert, never
  broken affordances.
- **`prefers-reduced-motion`** → no animated scrolling or transitions; jumps are
  instant.
- **Long / non-ASCII content** in model names, filter options, titles, tooltips
  → wraps and renders intact; no truncation or overlap.
- **Empty findings layer** → navigation, the three view regions, and their
  "no findings yet" empty states all still render.
- **Two runs, identical inputs** → byte-identical output except the "generated
  at" stamp; no interactive feature introduces a new non-deterministic field.
- **Stale or "no measurement" finding under an active filter/sort** → its
  marker is preserved; it participates in filter/sort like any other finding.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (non-regression)**: Every `001-findings-dashboard` requirement
  (FR-001..FR-015 of that spec) MUST continue to hold. v2 MUST NOT remove or
  weaken evidence-backed values, tooltips (what/how/evidence + links), stale
  flagging and its non-zero exit, read-only behaviour, single-command
  generation, self-containment, or the deep links.
- **FR-002**: The site MUST provide a persistent navigation control that lets
  the reader reach each of the three views (`#lineup`, `#board`, `#dead-ends`)
  in a single action from anywhere on the page.
- **FR-003**: The page MUST present clear visual hierarchy: a distinct header;
  three visually separated, headed view regions; lineup grouping by tier and
  board grouping/ordering by status; and a consistent typographic and spacing
  scale.
- **FR-004**: Status badges and the stale / "no measurement" markers MUST convey
  meaning by text (and shape), never by colour alone.
- **FR-005**: Comparison charts MUST render with no clipped or overlapping value,
  axis, or model labels at the generator's default width, and MUST include a
  value axis with gridlines.
- **FR-006**: The generator MUST produce a comparison chart for each headline
  metric that has at least two models to compare (not decode speed alone);
  a chart MUST NOT display any value not also present in a table with a
  tooltip, and every chart element MUST carry the same tooltip and source links
  as its tabular counterpart.
- **FR-007**: The reader MUST be able to filter the views in-browser by model,
  by tier, and by status, and to search by free text over finding titles and
  rationales; matching updates all three views live, shows a match count, and
  is clearable in one action.
- **FR-008**: Tables with more than one row MUST be sortable in-browser by each
  column; numeric columns MUST sort numerically and honour each metric's
  higher/lower-is-better direction for "best first"; stale / "no measurement"
  rows MUST sort to a consistent, documented position.
- **FR-009**: All interactive controls (navigation, filters, search, sort,
  chart elements, tooltips) MUST be fully keyboard-operable with a visible
  focus indicator, and MUST NOT convey information by pointer/hover only.
- **FR-010 (progressive enhancement)**: With JavaScript disabled, 100% of metric
  values, tooltip text, links, badges/markers, and all three views MUST remain
  present and readable; navigation MUST still resolve as in-page anchors; tables
  MUST render in a documented default order. Interactive enhancements MAY be
  absent but MUST NOT leave broken affordances.
- **FR-011**: All interactivity MUST be inline in the single `site/index.html`
  (no external scripts, styles, fonts, or network requests) so the site still
  opens from `file://` fully offline; any third-party asset MUST be vendored
  inline. No charting library and no JS framework/toolchain is added.
- **FR-012**: Interactive features MUST NOT mutate the filesystem or persist
  state across reloads; the generated document is the single source of truth,
  and filter/sort/search state resets on reload.
- **FR-013 (determinism preserved)**: Generation MUST remain deterministic —
  identical inputs produce byte-identical output with the "generated at" stamp
  as the only allowed difference. No v2 feature may introduce another
  non-deterministic field.
- **FR-014 (accessibility)**: The generated site MUST meet WCAG 2.1 Level AA for
  the content it renders: text contrast ≥ 4.5:1 (≥ 3:1 for large text and
  meaningful non-text UI), full keyboard operability, visible focus, semantic
  landmarks and headings, information not by colour alone, and honouring
  `prefers-reduced-motion`.
- **FR-015 (read-only preserved)**: The generator and site MUST remain strictly
  read-only with respect to `results/`, `profiles/`, and the oMLX
  configuration, mutating nothing but `site/index.html`.

### Key Entities

This feature changes presentation and in-browser behaviour, not the data model.
The v1 entities — **Finding**, **Metric**, **Source**, **Status**, **View** —
are unchanged. v2 introduces only view-time, non-persisted concepts:

- **Navigation target**: a named link to one of the three view regions.
- **Filter/query state**: the reader's current model/tier/status selections and
  free-text query — held in the browser only, reset on reload, never written.
- **Sort state**: the active column and direction for a table — browser-only,
  non-persisted.
- **Comparison chart**: an inline-SVG rendering of one headline metric across
  models, derived at generation time from the same resolved values as the
  tables (no new source of truth).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From anywhere on the page, a reader reaches any of the three views
  in exactly one action (navigation), by pointer or keyboard.
- **SC-002**: 0 chart labels (value, axis, or model) are clipped by the viewport
  or overlap another, across all generated charts at the default width — the v1
  clipped-label defect is gone.
- **SC-003**: Every headline metric with ≥ 2 comparable models has a comparison
  chart; charts cover more than decode speed alone.
- **SC-004**: Filtering by any model, tier, or status, or a text query, updates
  all three views with a visible match count and no page reload and no network
  request; a one-action clear restores the full page.
- **SC-005**: Every multi-row table is sortable by each column; numeric columns
  verifiably order numerically (not lexically) and respect metric direction.
- **SC-006**: The site meets WCAG 2.1 AA on the applicable success criteria:
  measured text contrast ≥ 4.5:1, every interactive control reachable and
  operable by keyboard with visible focus, and no information conveyed by
  colour alone.
- **SC-007**: With JavaScript disabled, 100% of metric values, tooltip text,
  and links remain present and readable, and all three views render.
- **SC-008 (non-regression)**: All six `001-findings-dashboard` success criteria
  (SC-001..SC-006 of that spec) still pass, generation stays under 5 seconds,
  and output stays byte-identical except the stamp.

## Assumptions

- Single local user (the maintainer); no authentication, hosting, or
  multi-user concerns — unchanged from v1.
- Python 3, standard library only; the generator gains rendering and inline
  CSS/JS emission, not new dependencies (constitution III). Charts remain
  generator-emitted inline SVG (v1 research R2).
- Inline client-side JavaScript is acceptable for view-time interactivity; it
  is authored to degrade gracefully (progressive enhancement) and adds no
  network path (constitution V) and no build toolchain (constitution VI).
- The findings layer schema is sufficient as-is; if a richer chart wants a
  metric not yet marked headline (e.g. memory footprint), that is a findings-
  layer edit (add/mark a metric), not a generator or schema change (v1 SC-003).
- FINDINGS.md and backlog.md remain the sources of truth; v2 changes how the
  findings layer is presented, never what it asserts.
- Test-First (constitution VII) binds: interactive behaviour is verified against
  the generated HTML/SVG structure (presence of controls, ARIA/semantics,
  ordering, no-clip geometry, deterministic bytes), not pixel snapshots.

## Out of Scope (v2)

- Dark / light theming and any colour scheme beyond a single clean default
  (deferred; `prefers-color-scheme` is not a v2 goal).
- A responsive / mobile redesign and a print stylesheet; v2 targets the
  desktop `file://` reader. Content MUST NOT truncate, but reflow to small
  viewports is not a goal.
- Rendering all 34 FINDINGS sections — that is backlog D8, a separate
  content-coverage feature over the same findings layer.
- Live data from the oMLX API, editing findings from the UI, and auto-deriving
  findings from `results/` — all remain out of scope as in v1.
- Persisting filter/sort/search state (URL, storage, or files), and any
  server-side or networked interactivity.
- Adding a charting library, a JS framework, or a build/bundler step.
