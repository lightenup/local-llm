# Feature Specification: Findings Dashboard

**Feature Branch**: `001-findings-dashboard`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "Extend the project with a dashboard showing our findings, with explanations in the UI (tooltips) on the metrics in the findings, so I'm on board with their findings. Tests and benchmarks used will evolve over time. Do not reinvent the wheel if something already exists."

## Context

This repo is an evidence-driven local-LLM stack. `docs/FINDINGS.md` (34 sections)
records what was measured and why; `docs/backlog.md` tracks open work;
`results/` holds 134 measurement files in heterogeneous JSON schemas. The
verdicts, p-values and "dead end" statuses live in the FINDINGS prose, not in
the JSON. The dashboard exists so a reader can audit and trust every number
without reading 2,700 lines of findings first.

Settled design decisions (2026-09-22, with the owner):

- **Curated findings layer.** One small structured file per finding, between
  the dashboard and `results/`. The dashboard never auto-derives findings from
  the raw JSON. This is the mitigation for "benchmarks evolve over time": a
  finding names the file and JSON path it depends on, so drift becomes a
  visible stale flag instead of a silent wrong number.
- **Static, self-contained HTML** generated by a Python script. No server, no
  network at view time, opens from `file://`.
- **V1 scope**: current lineup + headline metrics + candidate status board +
  settled dead ends. Full per-section FINDINGS rendering is a later feature.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Read the live lineup with evidence-backed numbers (Priority: P1)

The maintainer opens the dashboard and sees the models and profiles that are
currently served (quality tier, fast tier, and any additive models), each with
its headline metrics: decode speed, context ceiling, accuracy scores, memory
footprint. Hovering or focusing any metric shows a tooltip explaining what was
measured, how it was measured (which bench script, which suite, what settings),
and the evidence behind it (sample size, p-value, or "deterministic"), with a
link to the exact FINDINGS.md section.

**Why this priority**: This is the core value. The owner's stated goal is being
"on board with the findings" — a number without an explainable method is the
exact thing this dashboard must eliminate.

**Independent Test**: Generate the site with only the lineup view populated;
open it from disk; for every displayed number, verify a tooltip appears on
hover and keyboard focus, stating what/how/evidence, and that its link resolves
to a real FINDINGS.md section.

**Acceptance Scenarios**:

1. **Given** the findings layer contains the shipped lineup, **When** the site
   is generated and opened, **Then** every live model/profile is listed with
   its headline metrics and no number is displayed without a tooltip.
2. **Given** a metric whose source results file exists, **When** the site is
   generated, **Then** the displayed value equals the value resolved from that
   file at generation time.
3. **Given** a metric tooltip, **When** the reader opens it, **Then** it
   contains: what the metric measures, which bench script and suite produced
   it, the evidence (n, p-value, or deterministic), and a link to the
   FINDINGS.md section.

---

### User Story 2 - See the status of every candidate model (Priority: P1)

The maintainer sees a status board covering every model that has been
evaluated, each with a status (shipped / on-trial / retired / dead-end / open)
and a short rationale with its deciding measurement, so the history of the
lineup is legible without digging through git log and FINDINGS.

**Why this priority**: The repo's method is retirement-on-evidence; the board
is what makes that visible at a glance and prevents re-litigating closed
candidates (the backlog's "do not re-open" rule).

**Independent Test**: Generate the site with only the status board populated;
verify every evaluated model appears exactly once with a valid status and a
rationale that names the deciding measurement and links to its FINDINGS
section.

**Acceptance Scenarios**:

1. **Given** the findings layer covers the evaluated models, **When** the site
   is generated, **Then** each appears exactly once with one of the five
   statuses and a rationale.
2. **Given** a candidate marked retired or dead-end, **When** the reader opens
   its entry, **Then** the rationale names the measurement that closed it
   (e.g. the accuracy gap with p-value, or the residency cost) and links to
   the FINDINGS section.

---

### User Story 3 - See the settled dead ends (Priority: P1)

The maintainer sees the list of levers and ideas that were measured and
closed ("do not re-open"), each with the measurement that closed it, so
future sessions — human or agent — skip them instead of re-running them.

**Why this priority**: Half the value of this repo is knowing what *not* to
try. The backlog already carries this list in prose (§H); the dashboard makes
it the first thing a new session sees.

**Independent Test**: Generate the site with only the dead-ends view
populated; verify every entry from backlog §H appears with its closing
measurement and source link.

**Acceptance Scenarios**:

1. **Given** the findings layer contains the settled dead ends, **When** the
   site is generated, **Then** each is listed with the measurement that closed
   it and a link to the FINDINGS section or backlog entry.
2. **Given** a dead end that was closed by reasoning rather than measurement
   (e.g. a capacity calculation), **When** the reader opens it, **Then** the
   entry is marked "no measurement" and states the argument.

---

### User Story 4 - Add or update a finding by editing one file (Priority: P2)

When a new experiment lands, the maintainer adds or edits a single findings
file (title, status, metrics with tooltips, source references) and re-runs the
generator. The dashboard reflects the change. No generator code changes are
needed for a finding that references an existing results file.

**Why this priority**: Benchmarks evolve over time; if updating the dashboard
costs more than the experiment itself, the dashboard rots and stops being
trusted. One-file-per-finding keeps the marginal cost near zero.

**Independent Test**: Add a new findings file referencing an existing results
file; regenerate; verify the new finding renders with correct values and
tooltip, and that removing the file and regenerating removes it.

**Acceptance Scenarios**:

1. **Given** a valid new findings file, **When** the generator runs, **Then**
   the finding appears in the correct view with values resolved from its
   source references.
2. **Given** a findings file with a typo'd JSON path, **When** the generator
   runs, **Then** it fails with a message naming the file, the finding, and
   the unresolvable path.
3. **Given** a finding whose status changes (e.g. on-trial → shipped), **When**
   the file is edited and the site regenerated, **Then** the finding moves
   between views accordingly.

---

### User Story 5 - Stale sources are flagged, never silent (Priority: P2)

When a referenced results file is deleted or its schema changes so a JSON path
no longer resolves, the generator still emits the site but marks the affected
finding stale with a visible indicator, and exits non-zero so an unattended
chain notices.

**Why this priority**: This is the core guarantee for "benchmarks evolve over
time": the failure mode must be a loud, visible flag — never a silently wrong
or silently absent number.

**Independent Test**: Generate a valid site; delete one referenced results
file; regenerate; verify the site shows a stale marker on exactly that finding
and the generator's exit code is non-zero.

**Acceptance Scenarios**:

1. **Given** a finding whose source file no longer exists, **When** the
   generator runs, **Then** the site renders the finding with a visible stale
   marker and the generator exits non-zero.
2. **Given** a finding whose JSON path no longer resolves (schema drift),
   **When** the generator runs, **Then** the same stale treatment applies and
   the message names the path.
3. **Given** all sources resolve, **When** the generator runs, **Then** no
   stale markers appear and the exit code is zero.

---

### User Story 6 - Deep links from any metric to its raw sources (Priority: P3)

From any metric in the UI the reader can jump to the FINDINGS.md section that
argues the point and to the raw results file that carries the number.

**Why this priority**: Trust is ultimately delegated to the primary sources;
the dashboard is a lens, not a record. Links make the delegation one click.

**Independent Test**: For a sample of metrics, click through to the FINDINGS
section anchor and the raw JSON; verify both resolve.

**Acceptance Scenarios**:

1. **Given** a metric with a source, **When** the reader follows its links,
   **Then** the FINDINGS.md section anchor and the raw results file both
   resolve.
2. **Given** a finding with no measurement (a wiring decision), **When** the
   reader inspects it, **Then** it is marked "no measurement" and offers only
   the documentation link.

---

### Edge Cases

- A findings file references a results file that does not exist → stale
  marker per User Story 5; the rest of the site renders normally.
- Two findings reference the same results file → both render; no ownership
  conflicts.
- A finding has no source at all (judgement or wiring decision) → allowed,
  rendered with a "no measurement" marker.
- The findings directory is empty → the site renders with an explicit
  "no findings yet" message rather than an empty page.
- A new results file appears with no finding referencing it → it is not shown;
  the dashboard is curated, never a dump of `results/`.
- A FINDINGS.md section is renumbered → the link target is recorded as
  section number + title; the generator warns when the title no longer matches
  the heading at that number (known maintenance cost, accepted).
- Long tooltip text and non-ASCII content → wrapped and rendered intact, no
  truncation.
- Regeneration is run twice with unchanged inputs → byte-identical output.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST regenerate the complete site from the findings
  layer and `results/` with a single command.
- **FR-002**: The findings layer MUST be a directory of small structured files,
  one per finding. Each file MUST declare: a stable id, a title, a status, the
  model(s) it concerns, the FINDINGS.md section it belongs to, and one or more
  metrics.
- **FR-003**: Finding status MUST be one of: `shipped`, `on-trial`, `retired`,
  `dead-end`, `open`.
- **FR-004**: Every displayed metric MUST carry a tooltip containing: what the
  metric measures; how it was measured (bench script and suite); the evidence
  (sample size, p-value, or "deterministic"); and a link to the FINDINGS.md
  section.
- **FR-005**: Metric values MUST be resolved at generation time from the
  referenced results file and JSON path. Display values MUST NOT be hardcoded
  in findings files or templates.
- **FR-006**: The dashboard MUST present three views: the live lineup (models,
  profiles, headline metrics), the candidate status board, and the settled
  dead ends.
- **FR-007**: The generator MUST validate every findings file (required fields,
  known status values, well-formed source references) and fail loudly —
  non-zero exit, no site written — listing every problem found.
- **FR-008**: When a referenced results file is missing or a JSON path no
  longer resolves, the generator MUST still write the site, mark the affected
  finding stale with a visible indicator, and exit non-zero.
- **FR-009**: Tooltips MUST be triggerable by hover and by keyboard focus, and
  dismissible; no information MAY be hover-only.
- **FR-010**: The dashboard and generator MUST be strictly read-only with
  respect to `results/`, `profiles/`, the oMLX configuration, and the running
  server. They MUST NOT mutate, delete, or re-order any existing file.
- **FR-011**: The generated site MUST be self-contained: it MUST open from
  `file://` with no network access and no server. Any third-party library MUST
  be vendored into the repo.
- **FR-012**: Generation MUST be deterministic: identical inputs produce
  byte-identical output.
- **FR-013**: The v1 seed MUST cover: the live lineup (Qwen3.8-27B-8bit with
  its four profiles, the oQ4e fast tier, gemma-4-31B), the closed candidates
  (Coder-Next, Qwen3.8-Flash-Next, OptiQ, the qwen3_5_moe 35B-A3B class), and
  the settled dead-ends list from backlog §H.
- **FR-014**: Every metric in the UI MUST link to its FINDINGS.md section and,
  when it has a source, to the raw results file.

### Key Entities

- **Finding**: one evaluated claim about a model or lever. Attributes: stable
  id, title, status, model(s), FINDINGS section reference, metrics, rationale
  (for the status board), created/updated dates.
- **Metric**: one number inside a finding. Attributes: name, unit, direction
  (higher/lower is better), source reference (results file + JSON path),
  tooltip (what / how / evidence), optional baseline or comparator value with
  its own source reference.
- **Source**: a pointer into `results/` — file path plus JSON path. Resolved
  at generation time; the resolution outcome (value / stale / no measurement)
  drives rendering.
- **Status**: the lifecycle state of a finding — `shipped`, `on-trial`,
  `retired`, `dead-end`, `open`. Determines which view the finding renders in.
- **View**: a section of the dashboard — lineup, candidate board, dead ends —
  populated by findings of the matching status.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A first-time reader can determine, for any displayed number,
  what was measured, how, and where the evidence lives, in under 10 seconds
  using the tooltip and its links alone.
- **SC-002**: 100% of metric values displayed in v1 are resolved from
  `results/*.json` at generation time; zero metric values are hardcoded in
  findings files or templates.
- **SC-003**: Adding a new finding that references an existing results file
  requires exactly one new/edited findings file plus one generator run — no
  generator code change.
- **SC-004**: Generation completes in under 5 seconds against the current data
  volume (134 results files, seed findings set).
- **SC-005**: Deleting or schema-drifting any referenced results file produces
  a visible stale marker on exactly the affected findings and a non-zero
  generator exit — never a silent wrong or absent number.
- **SC-006**: The generated site opens from `file://` with no network access
  and no running server, and renders all three views correctly.

## Assumptions

- Single local user (the maintainer); no authentication, no hosting, no
  multi-user concerns.
- Python 3; standard library preferred, new dependencies justified in the plan
  (constitution III). A charting library, if used, is vendored locally.
- FINDINGS.md section numbers are stable enough to link against; renumbering is
  a known, accepted maintenance cost (generator warns on title mismatch).
- The findings layer is curated by hand or with agent assistance; the
  dashboard never auto-derives findings from `results/`.
- Results-file schemas will evolve; v1's mitigation is explicit JSON paths plus
  stale flags. Auto-migration of findings across schema changes is out of
  scope.
- No telemetry and no network at generation or view time (note: oMLX itself
  uploads accuracy suites with ≥100 questions to omlx.ai; that is the
  benchmark harness's behaviour, not the dashboard's, and the dashboard adds
  no new upload path).
- The dashboard is a lens over the record: FINDINGS.md and backlog.md remain
  the sources of truth; when the dashboard and the prose disagree, the prose
  wins and the findings layer is fixed.

## Out of Scope (v1)

- Rendering all 34 FINDINGS sections (later feature, same findings layer).
- Live data from the oMLX API (the dashboard is generated, not live).
- Editing findings from the UI (files are edited in the repo).
- Auto-deriving findings or metrics from `results/`.
- Multi-language support, theming beyond a clean readable default, and any
  deployment beyond opening a local file.
