Raising the concurrency limit

closed by measurement: p95 latency at 8 concurrent: 31.213 s

Concurrency is prefill-bound: eight concurrent requests buy 1.38x aggregate throughput and cost 4.9x p95 latency (28.42 t/s, p95 31.2 s vs 20.66 t/s, 6.4 s at one). Two are worse than one (scaling efficiency 0.44). Each client sent a distinct ~1,035-token cold prompt, so ~8,300 tokens of prefill consumed roughly half the wall; the engine's decode batching is fine — feeding it eight cold prompts is what does not scale. The lever for parallel agent work is prefix-cache hit rate, not the limit.

GLM-5.2 / Kimi-class models locally on 128 GB

no measurement closed by argument

Closed by argument: GLM-5.2 needs ~239-245 GB even at 2-bit and degrades below Q4, making a 256 GB Mac Studio the entry ticket. Expert streaming does not rescue it — streaming cost scales with active parameters, and GLM-5.2 is 40B active (~13 GB of expert reads per token at ~2.6 bits/param), so several GB come off SSD every token: sub-2 tok/s optimistically. Prefill is worse, since every prompt token routes independently and touches essentially all experts. The sane use of GLM-5.2 is remote, as a planner over its native API, with local doing execution.

FINDINGS §34

In-memory hot cache

closed by measurement: repeat median latency, cache off: 3.49 s

Measured worse on every number at a 20 GB cost: repeat median 3.96 s with hot_cache_max_size=20GB against 3.49 s with it off, cold 14.39 s against 12.58 s, and the cache hit fraction does not move at all (0.886 vs 0.884). Repeats already reuse 88% of their blocks from the SSD tier; the residual 3.5 s is prefill of the uncached tail plus generation, not disk reads. There is no disk-read cost left for a RAM tier to remove. The earlier 'largest remaining win for agentic loops' claim was a plausible hypothesis and it was wrong.

Glossary

role
The name a client calls through LiteLLM (coder, reasoner, fast, long, embed, rerank). A role maps to one model and profile, so the model behind it can change without touching any client.
tier
Where a shipped model sits in the lineup: quality (best answers), fast (best speed for good-enough answers) or additive (extra capability beside the other two). §19
profile
An oMLX model profile: one model with a fixed set of sampling, thinking and context settings, exposed under its own id such as Qwen3.8-27B-8bit:qwen-code.
oQ4e
An oMLX mixed-precision 4-bit quantisation: most weights at 4 bits, sensitive layers kept higher. oQ6e and oQ8e are the 6- and 8-bit versions. §19
MTP
Multi-token prediction: extra heads draft the next few tokens and the model verifies them in one pass, which speeds up decoding without changing the answer. §4
thinking
Reasoning text a model writes before its answer. It usually raises accuracy and always costs tokens and time; some models cannot switch it off. §42
gate
The cheap checks before any accuracy run (bench/candidate_gate.py): the architecture is supported, the model loads, its real memory cost, and that it serves a 16k prompt while the shipped lineup stays loaded. About 10 minutes. It says nothing about answer quality. §27
paired
Comparing two models on the same questions, question by question, instead of comparing their overall scores. It separates real differences from noise at sample sizes where overall scores cannot. §8
flips
In a paired comparison, the questions one model got right and the other got wrong, written as A/B. Only flips carry information; questions both got right or both got wrong do not. §8
McNemar
The significance test for paired right/wrong results, computed from the flips. A small p (below 0.05) means the difference is unlikely to be chance. §8
harness
The code that prompts the model and grades its answers; here, oMLX's bundled benchmark suites. An oMLX upgrade can change a prompt (0.7.1rc1 did for livecodebench), so scores only compare within one harness version. §41
16K cap
oMLX's livecodebench allows at most 16,384 answer tokens. A model that thinks longer is cut off and the answer counts as wrong, so a capped score understates such a model. §42
