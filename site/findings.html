The drafter's entire advantage disappears at batch 2 and never returns. This is the expected shape rather than a defect: speculative decoding wins by filling decode slots that a single sequence leaves idle, and a second concurrent sequence fills them for free. Once the batch does that job, drafting adds verification work for no gain, which is why the ratio sits marginally below 1.0.

Confirmed independently by the accuracy suites, which ran identical workloads at batch 8 with MTP on and off: wall-clock ratios of 0.99x to 1.07x across six suites, median 1.02x.

Two consequences:

  • The shipped configuration is correct for its actual use. opencode issues one request at a time, so the profiles really do get 1.74x.
  • Do not expect MTP to help throughput work. For batch serving it is neutral at best. It is also not worth disabling, since 0.99x is inside noise and switching would cost an engine reload.

Batching itself is a genuine aggregate win the drafter cannot provide: plain decode goes from 18.0 t/s single-stream to 92.2 t/s at batch 8, a 5.1x aggregate, at the cost of per-stream decode falling to 11.5 t/s. See §8 for why that aggregate does not survive contact with real HTTP concurrency.

Why base-model MTP (mtp_enabled) is not usable

The 8-bit checkpoint reports:

Config declares MTP layers but the weight files contain neither mtp.* tensors nor native nextn layers.

So the in-checkpoint MTP path is unavailable and import-mtplx does not apply (that needs an MTPLX side-car with mtp.safetensors + mtplx_runtime.json, which this repo does not ship). The separate drafter is the correct route here.

The exclusivity constraint that shapes every profile

omlx/model_settings.py::vlm_mtp_processor_conflicts disables vlm_mtp for any request needing a logits processor. To keep the 1.8× decode, every profile must leave these unset or neutral:

  • repetition_penalty — must be None or 1.0
  • presence_penalty — must be None or 0.0
  • guided_grammar_enabled — must be False

thinking_budget_enabled is safe — the MTP path applies it at verify time via MTPProcessingSampler. min_p: 0.0 was verified safe empirically (the qwen-code measurement above sets it and still gets 40 t/s).

profiles/definitions.py::validate() enforces this so it cannot regress.

6. Profile architecture

oMLX has two distinct merge paths (omlx/model_settings.py):

  • _settings_with_profile_locked → universal fields only, merged per request
  • _runtime_settings_with_profile_locked → universal + model-specific, and model-specific fields are part of the engine load-time variant signature (omlx/engine_pool.py::_variant_signature)

Therefore the design rule: one shared engine variant on the base model, profiles carry universal fields only. All four profiles report has_engine_fields: false, and a smoke run that exercises all four recorded 1 engine load total — confirmed zero-cost switching.

7. Client wiring (opencode)

The profiles are consumed through opencode, whose config is owned by ~/Development/private/dotfiles/opencode/opencode.json (symlinked to ~/.config/opencode/opencode.json). That repo documents the wiring; the measurements behind it are here.

  • Profile IDs survive opencode's parser. opencode splits provider/model with split("/", 2), so the colon in Qwen3.8-27B-8bit:qwen-code is safe. It reads only the config models map and does no /v1/models discovery, so every profile has to be listed explicitly.
  • Switching stays free through the client. After exercising two profiles via opencode, the VLMBatchedEngine loaded count in ~/.omlx/logs/server.log was unchanged, confirming the shared-variant design holds end to end and not just through the admin API.
  • Agents are pinned per profile (build→code, plan→reason, explore/general→agent, title/summary/compaction→agent), so the right sampling is used without manual switching. Verified from opencode's own header: plan · Qwen3.8-27B-8bit:qwen-reason.
  • Client timeout had to be raised to 45 minutes. Prefill at the 262k ceiling runs ~137 tok/s, so time-to-first-token on a full long-context prompt is about 32 minutes. The previous 15-minute headerTimeout would have killed it mid-prefill, making qwen-long unusable at the context it was built for.
  • Vision is real and was switched on. The checkpoint has language_model_only: false and 333 vision_tower.* tensors, so attachment: true and the image input modality are honest.

thinking_budget_enabled costs the entire MTP win

oMLX's vlm_mtp_processor_conflicts docstring states that thinking_budget_enabled is "intentionally absent" from the conflict list, because the MTP path applies ThinkingBudgetProcessor at verify time via MTPProcessingSampler, so "a thinking-budget default no longer forces the BatchGenerator fallback."

Correct for correctness, wrong for throughput. Measured on the reason profile, 400 generated tokens per run, same prompt:

reason profile settingdecode
as shipped (thinking_budget_enabled: True)17.6 t/s
thinking_budget_enabled: False31.9 t/s
preserve_thinking: False17.7 t/s (no effect)
both off32.4 t/s

For comparison, on the same prompt qwen-code and qwen-agent return 41.8 and 42.8 t/s. So reason was running at the plain-decode baseline while every other profile got the 1.8x, and thinking_budget_enabled is the single cause.

The budget exists so a hard prompt cannot spend unbounded tokens thinking; dropping it doubles throughput but the only remaining guard is max_tokens: 32768, which a runaway thinking episode could consume entirely and never reach an answer.

The throughput number alone could not decide it, so bench/thinking_budget_ab.py measured the risk the budget covers: four hard prompts, both arms, two repeats, recording reasoning tokens and whether each run terminated on stop rather than length. The decision rule was fixed in advance: the budget comes off only if no unbudgeted run exceeds 8,192 thinking tokens and none finishes on length.

**Result (results/thinking_budget_ab.json): the budget stays on.**

Four of eight unbudgeted runs exceeded 8,192 thinking tokens. The failure the budget exists to prevent happened on the first pass: algorithm_design repeat 1 generated all 32,768 tokens, finished on length, and never closed its thinking block, so the response carried no answer at all. Its sibling repeat consumed 30,149 thinking tokens and closed only just inside the cap.

So the cost is real and known (1.7x decode) and it buys protection against a roughly 1-in-8 total loss on hard prompts. The budget-on arm never came close to trouble: worst case 8,400 thinking tokens against a 32,768 hard cap. Note that the on-arm slightly overshoots its own 8,192 budget, because the MTP path applies the limit at verify time and a whole draft block can land past the boundary.

Sizing note: 8,192 is well chosen rather than lucky. The median hard prompt wants ~8,200 to 8,600 thinking tokens either way, so the budget is not truncating typical work; it clips only the tail.

A client-sent temperature was silently overriding every profile

This was a real defect in the setup, found while wiring up Spec Kit, and it made the sampling column in section 6 fiction for any request coming through opencode.

_effective_sampling_params in server.py resolves sampling as request > model settings > global:

if req_temperature is not None:
    temperature = req_temperature
elif model_settings and model_settings.temperature is not None:
    temperature = model_settings.temperature

opencode always sends a temperature — its documented default is 0 for most models and 0.55 for Qwen models — so qwen-code was not running at 0.7, nor qwen-agent at 0.3. Whatever the client picked won.

The fix is force_sampling: True on all four profiles, which takes the other branch and pins temperature/top_p/top_k to the profile, ignoring the request. It is a universal field, so it is free, and it is absent from vlm_mtp_processor_conflicts, so MTP is unaffected.

Verified by sending temperature: 0, top_k: 1, top_p: 1.0 (a greedy request) three times to qwen-code and getting three different sentences. Under the old behaviour all three would have been identical.

This is the intended contract: the profile is the sampling policy, and callers choose behaviour by selecting a profile rather than by sending knobs. A side effect worth knowing is that opencode's per-agent temperature/top_p are now inert against this provider.

force_sampling is deliberately not set on the base model, because bench/accuracy.py targets the base model and its --sampling deterministic mode has to keep working.

Suite scores were never going to settle this. qwen-code temperature 0.7 vs 0.3: no measurable difference, keep 0.7

The suite scores looked like a clean win for 0.3, moving the same direction on all three suites: humaneval 93.9 vs 92.1, mbpp 79.6 vs 78.4, livecodebench 59.2 vs 58.0. The paired test says otherwise.

The important column is the flip count. Temperature churns 108 of 500 livecodebench verdicts, roughly 22% of the suite, and the split is nearly even (51 against 57). The +1.2 point suite gap is the small net residue of a large amount of noise, not a signal. Pooled p = 0.27.

**qwen-code stays at 0.7**, the Qwen-published default, because nothing was measured that justifies moving it.

Caveat worth stating: both arms sampled at nonzero temperature, so these flips mix the temperature effect with plain run-to-run variance and the two cannot be separated from this data. A repeat of one suite at an unchanged temperature would size the pure variance floor. It would not change the decision, since the observed difference is already inside chance.

The wider lesson applies to any future sampling tweak here: a 500-sample suite score cannot resolve anything smaller than about 2 points, so judge sampling changes on paired per-question data or not at all.

Eight concurrent requests buy 1.38x aggregate throughput and cost 4.9x p95 latency. Two are worse than one.

This looks like it contradicts §4, where the engine reached 5.1x aggregate decode at batch 8. It does not, and the gap is the finding: these requests were prefill-bound, not decode-bound. Each of the eight clients sent a distinct ~1,035-token prompt with cached_tokens: 0, so about 8,300 tokens of prefill at ~500 t/s consumed roughly half the 31 s wall, while the aggregate t/s figure counts only generated tokens. The engine's decode batching is fine; feeding it eight cold prompts is what does not scale.

So the lever for parallel agent work is prefix-cache hit rate, not the drafter and not raising the concurrency limit.

Mixed profiles, one request per profile at once:

  • Zero engine loads. The shared-variant design of §6 holds under real concurrency, not just sequential switching.
  • Speedup over running them serially: 1.38x (16.8 s against 23.3 s).
  • Per-request slowdown: reason 1.68x, code 2.87x, agent 2.99x, longctx 3.56x.

This run replaces an earlier one that never reached its targets, kept as results/longctx_quality_uncalibrated.json. That run assumed a flat 3.1 characters per token and landed at 35,396 / 68,996 / 136,196 tokens, so the top row tested 136k while reporting 262k, and this section previously claimed quality above 136k was unmeasured.

The assumption was wrong in shape, not merely in value. Fitting the three lengths that run recorded gives, exactly to the token:

tokens = 0.1653855 * chars + 1796

There is a fixed ~1,800-token overhead — 240 section headers, the instruction text and the chat template — on top of a constant per-character rate, so no single ratio can hold across lengths: the same build measures 5.74 characters per token at 65k and 5.97 at 262k purely because that constant amortises. Picking a better constant would have failed the same way somewhere else.

bench/longctx_quality.py therefore no longer assumes a ratio. It sends two small probes of the real haystack construction, reads prompt_tokens back and fits the line at run time, which costs ~75 s once per run and lands within 8 tokens of a 261,824-token target. That also makes the harness survive a tokenizer change, which matters because backlog A1 puts a different model behind it. Two related defects were fixed alongside: haystack length quantised in ~8,256-token steps (the remainder is now padded to the character), and the console printed engine knobs while filtering out the *_enabled: False switches that made them inert, so a disabled accelerator read as an enabled one.

9. Cache and scheduler levers are API-reachable

An earlier revision of §8 recorded the hot cache as blocked behind a hand-edited settings.json and a server restart. It is not, in this oMLX build:

  • hot_cache_max_size and chunked_prefill are both fields on the admin GlobalSettingsRequest (omlx/admin/routes.py, cache and scheduler blocks).
  • POST /admin/api/global-settings persists them and then applies them at runtime. For cache fields it calls _apply_cache_settings_runtime, which updates the engine pool's scheduler config and unloads loaded models so the next load picks the new config up.
  • Only initial_cache_blocks, host/port and the MCP config path are documented in that handler as needing a restart. hot_cache_max_size is not among them.

So the cost of testing the hot cache is a model reload, not a server restart or a hand-edited config file. Omlx.update_global_settings() wraps it.

One asymmetry to know when verifying a change: the POST takes flat field names while the GET returns them nested under sections, so chunked_prefill goes in flat and comes back at scheduler.chunked_prefill, and hot_cache_max_size comes back under cache. Reading back the name you wrote returns nothing and looks like the write was ignored. Omlx.global_setting(name) searches both levels.

Two related capabilities were found while confirming this, both of which the earlier sessions worked around unnecessarily:

  • **POST /admin/api/cache/probe** classifies a prompt's blocks as hot-SSD, disk-SSD or cold. That is a direct instrument for prefix-cache behaviour, where before there was only the cached_tokens field on a completed request. bench/cache_ab.py probes before every request.
  • Restarts are automatable if ever needed. The server runs under the menubar supervisor, so POST /admin/api/server/restart returns 202 and the supervisor respawns it with about 7 s of downtime. omlx restart exists on PATH too. The endpoint is gated on OMLX_SUPERVISED, so it correctly refuses under a plain omlx serve.

14. What the variability check found, and why §13 needed correcting

Two questions were outstanding: how much of the measured difference is run-to-run noise, and whether livecodebench measures what its score implies.

The harness is exactly reproducible, so none of it is noise

bench/accuracy.py reason --suites mathqa --samples 500 re-run against the same model, same settings, compared to the original arm:

score43.8% both runs

Zero flips. Not "within chance" — identical, question for question. The engine is bit-exact too: six identical requests at temperature 0 produced six identical SHA-256 hashes.

Three consequences. Every cross-model flip in §13 is genuine model difference, so the McNemar p-values stand as computed. The variance floor that backlog B3 was parked against does not exist at these settings, so B3 can be closed rather than merely parked. And re-running a suite to confirm a result is pointless here — it would return the same numbers by construction. The planned 3.5-hour livecodebench re-run was cancelled on this basis.

livecodebench mostly measures I/O-contract compliance

The suite does not grade reasoning about code. omlx/eval/livecodebench.py extracts the last fenced block from the response, writes it to a temp file, runs it under python3 with a 30 s timeout and a 256 MB cap, and compares stdout exactly against the first three public test cases. A model loses the point for writing a function instead of a script, for guessing the input serialisation wrong, for printing true where the case wants True, or for being slow.

The prompt hands over a LeetCode-style description — "Return the maximum distance" — with an instruction to read stdin and write stdout, and never states how the inputs are serialised. Question 2857's test input is '5\n10', two values on separate lines. Coder-Next wrote map(int, input().split()), which reads one line, and died on the unpack. The algorithm was right; the guess was not.

The obvious implication, tested, and false

The decomposition above suggested the failures were cheap: if the suite never states its input serialisation, then stating it should recover most of them. That is a testable claim and bench/lcb_io_fix.py tested it. Sixty of Coder-Next's I/O-shaped failures were regenerated with a system prompt that spells out the contract — read all input from stdin robustly, the program must run and print, print only the answer, match boolean capitalisation, one code block — then extracted and executed through the identical path.

2 of 60 recovered. 3%. The failures came back in the same buckets: 42 crash_ValueError, 8 no_output. Projected across all 200 I/O-shaped failures in the suite, the score moves 0.432 to 0.445 against the 27B's 0.598.

A first attempt at this test capped generation at 4,096 tokens where the suite uses 16,384, which truncated long answers into no_output and would have overstated the failure. Re-run at the correct cap, no_output fell from 16 to 8 and ValueError rose from 37 to 42; the recovery rate barely moved. Seven of the sixty hit even the 16,384 cap, so Coder-Next writes very long answers on hard problems — a real cost of its own.

So §13's headline was right and this section's first draft was wrong

The taxonomy stands: Coder-Next's failures really are dominated by crashes rather than wrong answers, and it really does produce fewer wrong answers than the 27B, 71 against 79. What does not stand is the inference drawn from it. These are not convention mistakes a clearer prompt fixes. They reproduce under explicit instruction, deterministically, in the same buckets.

The honest characterisation is narrower and worse for Coder-Next: it is roughly as good at writing a correct function body and substantially worse at producing a complete, runnable program that honours an I/O contract. humaneval (-3.7) and mbpp (-0.2) ask for the former and show almost nothing. livecodebench asks for the latter and shows -16.6. That gap is real, not a scoring artifact.

For agentic coding this is the wrong weakness to have. Producing complete runnable artifacts is the job, not a benchmark conceit.

What the lineup becomes

Coder-Next is 2.0-2.5x the decode speed and 2.6-3.6x the prefill, at a real cost in end-to-end program correctness and a clear deficit in multi-domain reasoning (mmlu_pro -6.0, p=0.007, with no I/O contract to blame, as with hellaswag -4.4 and safetybench -5.4).

It is therefore a latency instrument, not a quality one: worth using where a verifier checks the output, where the task is bounded edits rather than whole-program generation, or where 262k of cheap context is the point. The 27B stays the default for anything whose correctness is not independently checked.

The lesson worth keeping

Three conclusions in one day, each overturning the last: the score said Coder-Next was far worse; the taxonomy said the score was an artifact; the remediation test said the taxonomy's explanation was wrong. Only the last was a prediction that could fail. Decomposing a result explains where it comes from but cannot tell you what it means — for that the explanation has to be turned into a claim about what should happen next, and then checked.

Prefix-cache audit (backlog B1b)

The cheap half of B1: check whether the shared prefixes opencode sends are byte-identical across calls, since one nondeterministic field silently converts a cache hit into a full prefill.

  • Skills are static. Nine SKILL.md files under ~/.agents/skills, no runtime interpolation; {{.MARP}} in ey-marp is documentation, not a template evaluated at send time.
  • The injected environment block carries a date. opencode prepends working directory, platform and today's date to the system prompt. The date changes the prefix once per day and the working directory changes it per project. Neither is per-request, so within a session the prefix is stable.
  • Placement limits the damage. The environment block sits after the bulk of the static instructions, so a date rollover invalidates the tail rather than the whole prefix.
  • One open risk: the available-skills list is injected after the environment block and is assembled from two directories. If that enumeration is not sorted deterministically it would reorder between sessions, which is exactly the silent cache-buster the working notes warned about. Not confirmed either way here; it needs POST /admin/api/cache/probe against a live session (B1a).

Client wiring, and the trap in reading §15 too eagerly

~/.config/opencode/opencode.json (symlinked into the dotfiles repo) now carries all seven model ids, and five agents moved to Coder-Next: title, summary, compaction, explore, general, plus small_model. build, plan, speckit and speckit-wide stay on the 27B.

The reasoning for that split is the thing worth recording, because §15 invites the opposite conclusion. opencode never does best-of-N — every call is N=1, and at N=1 §14 applies rather than §15. So Coder-Next takes the work that is speed-dominated and quality-insensitive, and the 27B keeps everything whose correctness nothing else checks. Moving build would have bought 2x decode on the main edit loop at exactly the weakness §14 identified.

Two details the model entries have to get right: Coder-Next is Qwen3NextForCausalLM, text only, so attachment is false and modalities.input is ["text"] — the 27B is a VLM and declares image input, and copying its entry across would advertise a modality this checkpoint does not have. reasoning is false for the same reason there is no cn-reason profile.

Residency was already correct and needed no change: the 27B reports is_pinned: true and Coder-Next does not, so Coder-Next is the one that pages out under pressure — which is the right way round, since the 27B is the quality default and carries the four profiles everything else depends on.

Verified end to end: opencode models omlx lists all seven, and opencode run --agent explore completed a real tool-calling task on cn-agent in 21.6 s.

16. The routing layer, and three things it does not do

LiteLLM behind Postgres, pinned by digest rather than tag — a tag can be repointed at a new image, which is what the 1.82.x malware advisory actually describes. One virtual key scoped to a local access group; a call to anything outside it is refused 403 before reaching any router, which pre-verifies the guardrail the cloud work will need.

Overhead is +21.1 ms median (direct 295.3 ms, proxy 316.4 ms, 9 interleaved repeats at max_tokens=1 so the hop is not drowned by decode). Reported as a fixed delta rather than a ratio, because a ratio taken on a 1 s request says nothing about a 20 min one. It is 0.167% of a 16k cold prefill and 2.1% of a 1 s request — so long-prompt work can move behind the proxy and short-prompt throughput measurement cannot. One request in nine cost +373 ms rather than +21 ms, almost certainly the spend-log flush.

Three things that do not work the way the plan assumed:

**max_budget does not enforce for local models, even with Postgres.** The database is necessary and not sufficient: local deployments carry no per-token pricing, so spend stays exactly 0.0 against a 5.0 cap no matter how much traffic runs. Token counts are logged per request, so usage tracking works; only the budget mechanism is dormant, and it stays dormant until real pricing arrives with a cloud provider.

**context_window_fallbacks is reactive, not proactive.** It fires only when the backend raises a context-window error. max_input_tokens in model_info is otherwise inert metadata that the router never pre-checks: a 4,059-token request against a deployment declaring 2,048 was served anyway, no fallback, no log line. The fix is router_settings.enable_pre_call_checks: true, after which the same request routed correctly. Found by shrinking the declared window rather than by paying a real 131k prefill — the mechanism is identical and the cost is 1/50th.

The corporate TLS proxy was a non-event. The root CA was already extracted and docker pull works through the inspection proxy untouched. The CA is mounted into the container's trust store but is inert: nothing in a local-only configuration makes an outbound TLS call, since oMLX is plain HTTP on the host. Do not record it as verified until a cloud provider exercises it.

Tool calls survive the hop intact, including Coder-Next's own function-call format, verified both as a single graded call and as a full opencode run task with file edits.

17. Best-of-N does not work here, and §15 says why it looked like it did

§15 concluded that sampling N against a verifier converts Coder-Next's speed into quality. Measured directly, it does not.

The instrument was wrong, not the arithmetic. Every cost figure in §15 — and the 1.75x / 2.40x / 4.84x figures produced while building the gate — compares a model against itself at a different N. Nobody faces that decision. The decision is between two things a request could be sent to, so both were run head to head on 12 livecodebench problems the sampler had actually failed, same verifier, same warm ~3.4k shared prefix:

armrecoveredwall-clockcorrect answers/min
Coder-Next best-of-4 + verifier2/12368.8 s0.33
27B 8-bit greedy, N=16/12390.9 s0.92

Three times the correct answers in the same wall-clock. §15 projected best-of-4 landing 1.32x faster at ~56.0 against 59.8; the measured reality is the same speed and a third of the answers.

Why it fails, mechanically: best-of-N and MTP compete for the same silicon. The speculative-decoding win that makes the sampler fast is single-stream only — 1.74x at batch 1, 0.99x at batch 2+ (§8) — so sampling N destroys the very advantage that was supposed to pay for the extra samples. Measured directly, per-stream decode collapses 63 → 26 tok/s from N=1 to N=4 while aggregate throughput rises only 1.67x. On hardware without speculative decoding the trade would look completely different. This is a property of this setup, not of best-of-N.

Two further mechanisms worth keeping, both found while costing it:

  • Prefix sharing inside one burst is partial and racy. N=4 cold on a 6k prefix returned cached=[0, 4096, 0, 4096] — two of four raced to prefill the same blocks and duplicated the work. §15's "a shared prompt is the batching best case" holds across calls, not within one.
  • The straggler dominates. Wall-to-all-complete is set by the slowest candidate; at temperature 0.7 output length varies enough that free-running generation cost 4.84x where an equal token budget cost 2.40x. Verifying candidates as they arrive and returning on the first pass recovers part of that, but cuts time-to-answer only — abandoned candidates keep decoding server-side, so the machine still pays for N.

What survives. bench/verifier.py — the runner, with ok and ran kept separate so "verifier rejected it" and "verifier never ran" can never be confused. What is closed is sampling N to pick a winner, not verification. Re-open only if the lineup loses MTP, or if a verifier appears whose pass@N recovery is far above livecodebench's 22%.

This section was written wrong twice before it was written right. Both wrong readings are recorded, because both were plausible and one is the obvious guess.

What the guard actually projects. For a 27B request with a single model resident, the KV+SDPA projection is linear in prompt length:

20. Prefix-cache hit rate under a real agent loop: 86.7%

§10 ranked this the highest-value unmeasured lever. Measured on a real opencode task — glob, read, edit — across 5 requests averaging 7,088 prompt tokens: 30,720 of 35,440 tokens reused.

That 30,720 is exactly 15 × 2,048, and the coincidence is the finding: the cache works in whole 2,048-token blocks. A 4,523-token prompt reuses exactly 4,096 on repeat; a 22-token prompt reuses zero, always, however often it is sent. So the achievable hit rate is bounded by floor(tokens/2048)*2048/tokens, and short calls are not slow to cache, they are structurally uncacheable.

The practical answer is therefore favourable: agentic loops are not paying cold prefill repeatedly, because at ~7k tokens a request clears three blocks comfortably. The date and cwd that opencode injects roll over daily but sit in the tail, where they invalidate at most one block.

Measure it with bench/cache_probe.py, which reports the delta between two marks. The cumulative cache_efficiency on /admin/api/stats is not usable on its own — it read 81.4% over 729 requests on a server that had served ~40 h of pathologically repetitive benchmark traffic.

21. Task-shaped metrics, and the three ways they mislead

bench/taskbench.py scores what is actually wanted from these models against deterministic verifiers rather than a judge: PlantUML renders, draw.io XML has a real mxGraphModel, Python behaves as asserted, tool calls are usable. It never touches the accuracy queue, so §11's upload does not apply.

The first version measured nothing. Sixteen tasks, both tiers scored 16/16, and the tool correctly reported "no significant difference" — a statement about the tasks, not the models. A task set everything passes is exactly as uninformative as one nothing passes. Difficulty is now verified by writing a reference answer for every hard task rather than assumed.

Three traps, each of which produced a confident wrong answer first:

Temperature confound. Comparing role aliases coder (temp 0.7) against fast (temp 0.3) showed the 4-bit model winning 27/27 to 24/27. That is sampling, not capability: force_sampling means the profile's temperature applies and cannot be overridden per request, so comparing aliases compares profiles. Like-for-like at 0.7 the direction reverses to 98% vs 91%. Compare profiles when choosing a profile; compare equal sampling when choosing a model.

Network-dependent verdicts. A model emitting !include https://raw.githubusercontent.com/... makes the verdict depend on GitHub; one task failed on a 404 with perfectly good diagram source. Those are now inconclusive rather than failures.

**The locally installed PlantUML rejects par ... and ... end** (1.2026.7, exit 200) while accepting par ... end, group, opt and break. Textbook-correct source that will not render on this machine — worth knowing before trusting any PlantUML output here.

Capability and reliability are reported separately because they disagree: 8-bit and oQ4e are identical on "passed at least once" (27/27 vs 26/27) and 98% vs 91% per attempt. And the harness prints its own power limit — 27 tasks resolve differences of roughly 15 points and up, so that 7-point gap is unmeasured, not absent. Removing the upload and the suite-score blindness does not manufacture statistical power.

22. Parameter count is not the lever on 128 GB — the GGUF probe, closed

Backlog B5 and A4. The question was whether a much larger model at lower precision beats the shipped dense 27B, and whether that justifies maintaining a second serving stack. Both answers are no.

The probe as specified could not run, and would have confirmed its own premise. 23. DFlash2: the drafter now exists, and it is a silent no-op in oMLX

Backlog B4 was parked because "dflash_draft_model needs a purpose-built block-diffusion draft checkpoint and no local model qualifies". That is no longer true — z-lab publishes a DFlash2 drafter for exactly Qwen/Qwen3.8-27B, and MLX builds of it exist. So the stated blocker lifted. The result is still no.

Assembling it takes three repos, none of which is sufficient alone: ProCreations/Qwen3.8-27B-DFlash2-MLXFast-Q4 has 4-bit weights and no config.json; KaedeTai/dflash2-mlx-quantized-draft has the config and no weights; cfontes/qwen3.8-27b-mlx-dflash2 is an MLX port of the code. The assembled drafter is architecturally sound: 175 tensors, 5 layers, 94 quantised tensors at 4-bit/group-64, hooking target layers 5–61 against the 27B's 64, with hidden_size 5120 matching on both sides.

oMLX only scans models at startup. The drafter was invisible until a restart via POST /admin/api/server/restart, after which oMLX registered it correctly as is_helper: True, engine_type: batched, 1.24 GB. An earlier conclusion that oMLX "cannot consume it" was premature and wrong — it simply had not looked.

It configures cleanly and does nothing. oMLX accepted dflash_enabled: true with the drafter (it enforces exclusivity with MTP — "choose one speculative-decoding path"), reloaded without error, and then decoded at dense speed:

Tests passed and both real defects still shipped

52 tests, 0 failures, and the two bugs a human found in under a minute of play both survived:

  • Non-uniform canvas scale — setTransform scaled X and Y independently, so every circle rendered as a ~2.8:1 ellipse. No test asserted the transform was uniform, because nothing in the spec said it had to be.
  • A units mismatch — constants documented px/step were tuned for 60 Hz while the loop ran at 120 Hz, making everything move at double speed. This passed every test because the tests asserted per-step values that were consistently wrong together.

The second is the instructive one. The suite verified internal consistency, not external correctness: it never asked how long a pipe takes to cross the screen in seconds. A model will happily produce a self-consistent world with the wrong constant in it, and a test suite written by the same model in the same context will agree with it. At least one assertion per subsystem should be in human-meaningful units — seconds, pixels of travel, real-world rates — because those are the ones a self-consistent error cannot satisfy.

Neither bug was an implementation slip. Both were specification gaps, which is also why they were invisible to a phase (analyze) that checks artifacts against each other rather than against reality.

The verifier that was built for exactly this never ran

What this does not establish

Causation. A prediction of mine was falsified, which is the useful part. Disposition

Use Spec Kit selectively rather than by default. It earns its cost where the artifacts are the deliverable, or where several people must agree on a spec before code exists. For solo build-and-iterate against a written standard, one run each says it cost 979 lines of artifacts and 31 extra tests without buying defect protection — and that is a weak claim on one sample, so the disposition is "stop defaulting to it", not "stop using it".

The transferable habit is B's, not the workflow's: tests that assert against the standards document. That is available in either workflow and belongs in the constitution regardless of which one is chosen.

26. Qwen3.8-Flash-Next: fast, genuinely accelerated, and it cannot share the machine

§22 closed "parameter count is not the lever on 128 GB" against GGUF MoEs and dismissed this checkpoint in passing, on the grounds that qwen4_exp is "a different architecture, not a scaled-up Qwen3.8". That was the right reason to test it rather than to skip it: three of every four layers are Gated DeltaNet with a fixed recurrent state, so it does not obey §22's arithmetic. Measured with Jundot/Qwen3.8-Flash-Next-oQ4e-mtp (106.3 GB on disk, 125B total / 6B active, plus a 51.2B hashed n-gram table and a 4B Lightning MTP head).

Two of the three questions came back positive, and the third disqualifies it from the lineup as it stands.

It does not coexist — and this is what closes it

results/flashnext_residency.json, alternating 6000-token prompts against the 8-bit for 3 rounds:

  • An unload does not release synchronously. Loading immediately after one was refused against the dynamic ceiling while the pool still reported the old figure. Every script here now waits for current_model_memory to drain.
  • 3 evictions across 6 calls. Both models can be held (69.4 + 28.2 GB fits under the 107.52 GB cap), but a call that lands on Flash-Next costs a median 63.5 s against the 27B's 3.9 s, and the reload dominates that, not the prefill. That is 3x the ~20 s alternation that retired Coder-Next (A2c).
  • The weights are not what fails to fit — the KV is. Two resident models leave ~10 GB, and a 6000-token prompt does not fit in it. This is §18's prefill guard, in the shape §18 predicted.

The refusal was a pinning artifact, and oMLX is already a llama-swap

A first draft of this section read the failed load as "the admission guard does not evict to make room, it refuses". That is wrong, and the correction matters more than the original claim. All three lineup models carry is_pinned: true; engine_pool._find_lru_victim skips pinned, in-use, and actively-generating entries; so with the whole lineup pinned there was nothing evictable and the load raised InsufficientMemoryError — whose message ends "or unload another model".

(The field is spelled two ways, which costs a query to discover: pinned in /admin/api/models, is_pinned in a model's settings and in the PATCH body.)

Everything a model swapper needs is already in the pool:

evicts to the soft watermark before new weights allocateadmission pathactive

So the 3-of-6 evictions were that mechanism running, not a failure of it. The 8-bit is pinned and Flash-Next is not, which made Flash-Next the only possible victim: reloaded on its turn, evicted on the 27B's. The measurement is therefore better read as the price of automatic swapping on this hardware, 63.5 s versus 3.9 s resident — not as evidence that swapping is missing.

Unpinning the lineup would not buy coexistence. It converts a loud refusal into quiet thrashing at the same 63.5 s. And an external swapper (llama-swap and kin) is a step backwards here: it supervises one process per model, so it either duplicates the 69 GB or drops the oQ quant, in-checkpoint MTP and PLE offload that make this checkpoint viable at all, and it cannot reach inside oMLX's pool.

The circularity worth naming: cold load 30.9 s, warm 12 s. A fast swap needs ~69 GB to stay in the page cache, which is the memory the swap was freeing. Swapping here can be made deliberate, not cheap.

Disposition

Not a tier, on the evidence so far. It is a replacement-only model that decodes like the 16 GB fast tier while occupying 69.4 GB and evicting everything else. The fn-* proxy entries exist for benchmarking and are deliberately wired to no role alias.

What is still unmeasured, and could still change the verdict: the axis the vendor actually claims. DeepSWE 58.7 vs 42.2 and JobBench 55.7 vs 33.4 are agentic, and §14 found livecodebench blind to exactly that. task_flashnext (needs the proxy restarted to pick up the fn-* entries) and the paired code suite against acc_ship_code are both still to run. If the agentic gap is real and large, a 63.5 s model swap on an explicit "hand this to the big model" gesture is a different proposition from a 63.5 s swap on every routing decision — which is the mechanism the backlog now carries as A6c.

**The cheapest lever found is ttl_seconds, and it is unset.** The waste is not the swap, it is holding 69.4 GB after the last agentic call; a per-model TTL makes the model self-evicting and costs nothing while it is idle. Pinning policy then decides who the victim is, which is a routing decision wearing a memory setting's clothes. Raising memory_guard_tier from balanced to aggressive is the third lever and the one to reach for last, because it buys headroom by shrinking exactly the prefill margin §18 exists to defend.

Thinking works and costs 3.1x the tokens. results/fn_thinking.json, 4 tasks x 5 repeats x 3 arms: thinking-off 48.91 tok/s at 77 median completion tokens, thinking-on 44.23 tok/s at 171, no cap hits and no empty completions in 60 calls. The template defaults thinking ON at reasoning_effort: xhigh, the inverse of every other model here, and bench/accuracy.py has no chat_template_kwargs path — so the preflight in bench/flashnext_thinking_ab.py gates the code suite rather than trusting it. It passes: thinking-off emits 0 reasoning characters against thinking-on's 393.

Left open deliberately: the tool-call bias above. It is the only quality concern this run raised, and it does not need settling while the arm is unwired.

The structural limit, stated plainly

Both arms sit at 95% per attempt after three rounds of deliberate hardening. Thirteen tasks that literally could not fail have been fixed, counts and geometry and connectivity and negative constraints are all checked, and two strong models still pass essentially everything.

33. Wiring plan, and why gemma's context ceiling is probabilistic rather than a number

§32 set gemma-4-31B's cap at the verified 65,536 and left the true limit unbisected in (65536, 131072]. That mattered for one decision only — whether build, which works on whole repositories, could move — so it was worth finding. bench/ctx_bisect.py bisects on the prefill guard, which is deterministic, so four probes settle it.

 98304 -> ADMIT (98,215 actual)      122880 -> ADMIT (121,177)
114688 -> ADMIT (112,755)            126976 -> ADMIT (124,938)
                                     131072 -> REFUSE

So the guard admits ~127k, nearly twice §32's verified figure. But admitting is not attending, and it is also not reliably admitting:

Two self-inflicted measurement errors, both worth recording

The first bisection run reported retrieval 0/3 and would have concluded "gemma cannot attend at 116k", which is false. Both causes were mine:

  1. The retrieval check set the profile window to lo + 4096 — a length already known to be refused — then sized the prompt at the boundary and made it longer by inserting the needle. Every probe tipped over the guard. A measurement taken at the exact edge of a cliff measures the cliff.
  2. The probe's own KV was still resident when the next call was made, so the guard counted memory that was about to be freed. The model is now unloaded and reloaded between the bisection and the retrieval check.

The same residue produced a spurious wiring failure: bench/verify_wiring.py reported plan as unreachable when run immediately after a 126k prefill, because a two-word prompt was refused on memory. It passed before and after. Sequencing a measurement after a memory-heavy one is itself a confound.

It is the one role the evidence unambiguously supports: reasoning-dominated (+9.0 mmlu_pro, p = 0.00006), not latency-critical (0.54x decode is invisible on a planning turn), and rarely above 65k. build, qwen-long and every other agent are unchanged.

Where the two frozen numbers come from

Read from /Applications/oMLX.app/Contents/Resources/omlx:

  • **current** — Scheduler._current_usage_bytes(refresh_mlx_active=False) (scheduler.py:4427). Its docstring is explicit: "Event-loop callers such as early preflight use the cached executor sample". The preflight gate runs on the event loop, so it reads _last_mlx_active_memory_bytes, which is only rewritten by a scheduler step on the MLX thread. No step runs while every request is rejected, so the sample never moves.
  • **transient** — _predicted_chunk_transient (scheduler.py:3853) returns max(base_prediction, static_per_token * n * 1.3 + recent_reclaim). recent_reclaim_bytes is memory a preceding preflight LRU eviction released, charged back on the theory it will be re-allocated. It is the only size-invariant term, which is why 35.43 GB is identical at min_chunk=32 and min_chunk=17. It cannot be the observed-max term: that is clamped at _OBSERVED_MAX_CLAMP_BYTES = 4 GiB (prefill_transient_tracker.py:34). recent_reclaim_bytes is zeroed only by PrefillTransientTracker.update(), i.e. on completion of a prefill chunk.

So it is a deadlock, not a shortage. A preflight eviction frees ~35 GB, books it as a predicted re-allocation, and that charge is cleared only by a prefill that the charge itself forbids. Running preflight LRU eviction for request preflight precedes every one of the six rejections.

What clears it

Unload and reload the affected model — it rebuilds the Scheduler, so both the cached sample and the tracker start empty:

15-token prompt      ADMITTED  0.8 s      <- the shape refused at 22:32
18,416-token prompt  ADMITTED  24.0 s     <- 768 tok/s, the healthy rate

Zero rejections since. A server restart works too; nothing else measured here does. Note what does not clear it: a successful large prefill on the same model. The 70,028-token probe at 22:29:22 went through (199.6 s, 350 tok/s — depressed by 5.5 GB of swap) and the very next small request was still refused at 22:32:25, because that probe entered through a path that bypassed the frozen preflight gate rather than refreshing it.

Raising iogpu.wired_limit_mb or the tier would also have papered over it by lifting the cap above the phantom 101.05 GB. Both were declined as the fix: the arithmetic being defended against is fiction, and permanently widening a safety margin to accommodate a stale reading trades a recoverable 400 for the Metal OOM crash the guard exists to prevent. Tier fractions, for the record (process_memory_enforcer.py:_PREFILL_ABORT_MARGIN): safe 0.90, balanced 0.90, aggressive 0.95, custom 0.95. §18 and §32 both quote 102.14 GB as the operative ceiling, which is 0.95 x 107.52 — the aggressive/custom figure, not balanced's 96.77. Those sections were measured under a different tier setting than the one shipping today.

ttl_seconds is inert on a pinned model

§26 called the unset per-model TTL "the cheapest lever, and it is unset". It is cheaper than that: on this lineup it does nothing. engine_pool.py:3120 skips entry.is_pinned before it ever reads settings.ttl_seconds. Measured: Qwen2.5-Coder-3B-8bit, ttl_seconds=60, pinned, zero traffic, still resident at t+240 s.

TTLs are now set — Coder-3B 600 s, oQ4e 1800 s, 8-bit 3600 s — and every one of them is a no-op until the model it is on is unpinned. Unpinning is a routing decision, not a memory setting (§26): it elects the eviction victim. Left as is.

Carried forward

  • Read the log, not the 400. The admission terms: line (scheduler.py:4116) breaks the bound into predicted_transient / observed_max_bytes / ane_prefill_transient_bytes. It only fires on the mid-prefill path; the preflight path that produced these six rejections prints no such breakdown, which is why the terms had to be re-derived from source here.
  • **bench/memory_probe.py cannot parse this message.** Its regex wants ceiling is ([\d.]+) GB; the current format says ceiling 107.52 GB. It has been silently unable to read a refusal since the message changed.
  • A repeated guard refusal at a small prompt means reload the model. It does not mean the lineup is too big. That distinction is worth a doctor check.
